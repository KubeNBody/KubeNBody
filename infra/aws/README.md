# KubeNBody on Amazon EKS

Terraform for an EKS deployment, and a Makefile that drives it and the deploy of the
`configs/aws/` overlay of `configs/base/`. The cluster is ephemeral: `make up` creates it
and restores the data, `make down` backs the data up to S3 and destroys it, so between
sessions only the base stack's storage is paid for.

| Directory | What |
|---|---|
| `bootstrap/` | S3 state bucket |
| `environments/prod/base/` | Permanent: VPC (public subnets, no NAT, S3 endpoint), ECR (app and mirror repositories), backup bucket, SSM parameters |
| `environments/prod/cluster/` | Ephemeral: EKS with node groups `system`, `workercpu` and `gpu`, add-ons, IRSA roles (ESO, pgBackRest, EBS CSI) |
| `modules/` | `networking`, `ecr`, `storage`, `params`, `eks`, `irsa` |
| `scripts/` | `configure.sh`, `init-secrets.sh`, `mirror-images.sh`, `minio-sync.sh` |

## Safety

- **AWS profile.** The Makefile ignores an inherited `AWS_PROFILE`, which may belong to
  another account, and uses `NBODY_AWS_PROFILE` (default `nbody`). Every target that calls
  AWS checks that the caller is in `ACCOUNT_ID`, both Terraform stacks pin `allowed_account_ids`, and
  `build-and-push.sh --aws` checks the account before building. Use `--profile nbody` for
  manual `aws` commands.
- **kubectl context.** Every kubectl call names the cluster's context, `nbody-eks`, so a
  deploy cannot land on another cluster in your kubeconfig. `make connect` writes the
  profile into the kubeconfig exec entry.
- **No account IDs in git.** Session values (ECR host, role ARNs, bucket, your IP) live in
  the gitignored `configs/aws/session/`, generated by `make configure`.

## Prerequisites

- Terraform ≥ 1.11 (S3-native locking; `make` refuses older), `aws` CLI v2, `kubectl`,
  `kustomize` (standalone — the overlay uses cross-tree bases + Helm), `helm`, `docker`
  with buildx, `python3`, `curl`, `openssl`, optionally `kubeconform`.
- An AWS profile named `nbody` for the account to deploy into (or set `NBODY_AWS_PROFILE`).
- Two globally-unique bucket names (state, backups).
- The region is `eu-central-1` unless `REGION` is set, the same on every `make` call.

```bash
cd infra/aws
export ACCOUNT_ID=<12-digit account id>
export STATE_BUCKET=<unique-state-bucket>
```

## One-time setup (permanent base stack, ~$1–3/month)

```bash
make preflight         # G (T4) and standard vCPU quotas, AZ offerings -> pick worker_zone
                       # new accounts often have 0 G vCPUs: request at least 4 early
make bootstrap         # state bucket

cp environments/prod/base/terraform.tfvars.example    environments/prod/base/terraform.tfvars
cp environments/prod/cluster/terraform.tfvars.example environments/prod/cluster/terraform.tfvars
#   base:    backup_bucket_name (+ azs if worker_zone isn't among the first 3)
#   cluster: worker_zone (from preflight)
make init              # both stacks
make plan-base && make base
make init-secrets      # real SSM values (placeholders until then)
make mirror-images     # third-party images -> ECR mirrors

export ECR_REGISTRY=$(cd environments/prod/base && AWS_PROFILE=${NBODY_AWS_PROFILE:-nbody} terraform output -raw ecr_registry)
../../scripts/build-and-push.sh --aws <tag>   # app images -> ECR, tag -> configs/aws
```

## Each session (ephemeral cluster, ~$0.67/h while up)

```bash
make up                # cluster-apply -> connect -> configure -> deploy-k8s -> MinIO restore -> Postgres wait -> verify
make endpoints         # dashboard and Grafana URLs, NBODY_API_URL for scripts
make scale-worker-cpu N=4    # workers / GPU start at 0
make scale-gpu N=1
make down              # final pgBackRest + MinIO backups, delete LBs/volumes, destroy cluster
```

These scale the node pools. The worker Deployments start at zero too: start the ones you
need, e.g. `kubectl --context nbody-eks -n nbody scale deployment worker-monolithic-cpu
worker-distributed-v2-cpu --replicas=4` (GPU: `worker-monolithic-gpu`,
`worker-distributed-v1-gpu`, `worker-distributed-v2-gpu`), and scale them to zero before the pool. Log in to the dashboard as `user`
with the password `make init-secrets` set or printed.

`make up` restores Postgres from the last finished session and MinIO from its S3 copy, so
data carries over between sessions. It only reports success once Postgres serves (every
instance set and pgBouncer at readyReplicas == replicas — this includes waiting for the
restore); `PG_WAIT_MIN` (default 45) bounds the wait, and on timeout it lists the restore
and instance pods.

**pgBackRest generations.** Each session writes its own repo path
`s3://<backup>/pgbackrest/nbody-db/<generation>`. `CURRENT` (an S3 object next to them)
names the last generation that got a successful final backup at `make down`; the next
`make up` restores **from** it (Crunchy's clone-from-S3 pattern) into a **new** generation,
so two clusters never share a repo. `ACTIVE` pins the running session's generation, so
re-running `make configure` mid-session never moves a live cluster's repo.

**`make down` order** (stops before deleting anything if a backup fails): pgBackRest full
backup → MinIO → S3 → `CURRENT` moved → delete `nbody`/`monitoring` namespaces → wait until
no NLB is left in the VPC and no PV remains → `terraform destroy` (cluster stack only) →
post-check for leftover EBS volumes / `k8s-*` security groups. `SKIP_BACKUP=1` skips the
backups (`CURRENT` stays at the previous generation). Stop submitting jobs before
`make down`: anything written after the final backup is lost.

**If a session dies without `make down`** (cluster destroyed by hand, laptop gone): its
generation still holds its backups + WAL in S3, but `CURRENT` points at the previous one.
The next `make up` stops at `configure`, before anything is deployed: the `ACTIVE`
pointer records another cluster's OIDC issuer. It prints the dead session's generation and
two ways on. To restore that session's data, point `CURRENT` at it and delete `ACTIVE`
(the printed commands), then run `make up` again. To start from `CURRENT` anyway, run
`make up ACCEPT_STALE=1`.

Grafana's NLB only admits your `/32`. If your IP changes: `make configure deploy-k8s`.

## Checks after `make up`

`make up` ends with `make verify`. After a first bring-up, also check:

1. ExternalSecrets are `SecretSynced` (IRSA and Parameter Store work) and PVCs are `Bound` (EBS CSI works).
2. `pgbackrest info` in the database pod shows repo1 on S3 with WAL archiving working.
3. The dashboard is reachable and you can log in. Grafana is reachable from your IP only.
4. `make scale-gpu N=1`, then the node advertises `nvidia.com/gpu` and a GPU job runs.
5. `make down` and `make up` again: the jobs and files of the first session are back (a restore drill).

## Offline checks

`make fmt`, `make validate` (all three stacks, in an isolated `TF_DATA_DIR` so a live
session's backend is untouched), `make render` (example session values, full + staged
build, NLB check, kubeconform). `render` refuses to overwrite a real session (`FORCE=1` to
override).

`make connect` writes the `nbody-eks` kubeconfig context but leaves your current-context
where it was.

## Teardown of the base stack

Meant to be permanent. To remove everything (after `make down`), run in `environments/prod/base`
with `AWS_PROFILE` set to your profile and the region you deployed to (`-var region=$REGION`
in both commands when it is not the default):

1. `terraform apply -var account_id=$ACCOUNT_ID -var allow_destroy=true` — in-place flag flip
   only (ECR `force_delete`, bucket `force_destroy`); without it, non-empty repos and the
   backup bucket refuse to delete.
2. `terraform destroy -var account_id=$ACCOUNT_ID -var allow_destroy=true`.
3. The state bucket has `prevent_destroy`: delete every object version, then the bucket,
   with the CLI; then remove `bootstrap/terraform.tfstate`.
